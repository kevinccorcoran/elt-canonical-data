# EDGAR Fundamentals (raw layer)

Company fundamentals from SEC EDGAR, stored exactly as reported in the
`edgar` schema of the main Postgres, so they join to prices and tickers.
Raw only: no ratios, no tag mapping, no cleaning. The indicator layer
(P/E, EV/EBITDA, ROIC, ...) is built on top of this later.

| | |
|---|---|
| Source | `data.sec.gov` XBRL APIs: companyfacts, submissions, `company_tickers.json` |
| DDL | `tools/create_edgar_schema.sql` |
| Loader | `src/datapipeline/ingestion/edgar_to_raw_etl.py` (`--mode bulk` / `--mode daily`) |
| DAGs | `raw_ingest_edgar_bulk` (manual, once), `raw_ingest_edgar_daily` (05:30 Amsterdam) |
| Tests | `tests/data_quality/test_edgar_raw.py`, `tests/ingestion/test_edgar_parsers.py` |
| Open issues | `tools/edgar_open_issues.sql` |
| Full statements | `tools/create_edgar_statements_schema.sql`, `edgar_statements_to_raw_etl.py`, DAG `raw_ingest_edgar_statements` (§7) |

## 1. Tables

| table | one row per | key | notes |
|---|---|---|---|
| `edgar.facts` | version of a tagged number | `(cik, fact_key)` | **insert-only**. ~125M rows, ~32 GB with indexes |
| `edgar.facts_quarantine` | fact whose period ends after its filed date | `(cik, fact_key)` | same columns; ~25k rows; see §3 |
| `edgar.filings` | filing per CIK, filed 2009+ (all forms) | `(cik, accession_number)` | **insert-only**. ~10.7M rows |
| `edgar.companies` | CIK with XBRL facts | `cik` | name, SIC, current tickers. Latest values only |
| `edgar.company_tickers` | SEC ticker map entry | `(cik, ticker)` | `first_seen_at` / `last_seen_at` build history over time |
| `edgar.load_runs` | loader run | `run_id` | window, counts, status |

`edgar.facts` columns map 1:1 to companyfacts JSON:

| column | JSON | meaning |
|---|---|---|
| `cik` | `cik` | TEXT, 10 digits, zero padded (`'0000320193'`). Same as `raw.ticker_metadata.cik` |
| `taxonomy`, `tag` | facts keys | e.g. `us-gaap` / `RevenueFromContractWithCustomerExcludingAssessedTax` |
| `unit` | units key | `USD`, `USD/shares`, `shares`, `EUR`, ... |
| `value` | `val` | NUMERIC, exact JSON text |
| `period_start`, `period_end` | `start`, `end` | `period_start` is NULL for instants (balances, share counts) |
| `fiscal_year`, `fiscal_period` | `fy`, `fp` | **of the filing**, not of the period |
| `form`, `accession_number`, `filed_date` | `form`, `accn`, `filed` | the filing that reported this version |
| `frame` | `frame` | SEC's calendar label. **Hindsight**, see §2 |
| `fact_key` | | md5 of the natural key, generated by Postgres |

The data is long, not wide: there is no "revenue" column. Revenue for a
quarter is a row, found by tag and period. Apple's revenue alone sits under
three tags over the years (`SalesRevenueNet` to FY2017, `Revenues` in FY2018,
`RevenueFromContractWithCustomerExcludingAssessedTax` since), which is why raw
keeps every tag and the mapping belongs to the next layer.

## 2. The point-in-time rule

Look-ahead has broken a backtest in this project before. These rules are
what keep it out.

1. **A fact version is known from its `filed_date`, and usable from the next
   trading day.** Over half of 10-K and 10-Q filings are accepted after the
   16:00 close on their own filing date (51.6% of 11,414 filings checked
   against SEC's RSS acceptance times; only 12.8% land before the open). A
   strategy that trades at the close of `filed_date` would see the number
   before the market did. A few filings (4 of 20,917 in 2024q4) carry
   a filed date one to three days before SEC accepted them (SEC filing-date
   adjustments). Where `edgar.fsn_submissions.accepted_at` is known, the safe
   as-of date is the later of `filed_date` and the acceptance day.
2. **Take the newest version filed on or before the as-of date.** Every
   restatement is its own row. Apple's FY2009 revenue was $36.5B in the
   10-K (filed 2009-10-27) and $42.9B in the 10-K/A (2010-01-25). On
   2009-12-31 only the first was known.
   ```sql
   SELECT DISTINCT ON (cik, tag, unit, period_start, period_end) *
   FROM edgar.facts
   WHERE filed_date < :trade_date          -- strictly before: next-day rule
   ORDER BY cik, tag, unit, period_start, period_end, filed_date DESC;
   ```
   If one filing reports two values for the same period, both rows are
   kept. The indicator layer has to choose (for example the larger
   accession, or the value repeated in the next filing).
3. **Select periods by `period_start` / `period_end`, never by
   `fiscal_year`.** `fiscal_year` belongs to the filing: the FY2022 10-K
   repeats FY2020 revenue with `fiscal_year = 2022`.
4. **Never use `frame` to pick a value.** SEC assigns it after the fact to
   one version per calendar period, so it encodes which version won later.
5. **Never use `period_end` as an availability date.** Numbers arrive weeks
   after the period closes.
6. **Do not use `edgar.filings.acceptance_datetime_raw` for timing.** It is
   SEC's submissions string as sent. Compared with the RSS feed's exact New
   York times it is true UTC for some filings and off by plus or minus the
   New York UTC offset for others, with no field that says which.
7. **`edgar.companies` is current, not historical.** Names, SIC codes and
   tickers are today's values.

Filed dates are conservative. The market usually hears revenue and EPS from
the 8-K earnings release a few days before the 10-Q or 10-K, so the
fundamentals arrive later than reality, never earlier.

## 3. Quarantined facts

About 25k facts (0.02%) have a `period_end` after their `filed_date`. They
are SEC's own as-reported data: forecasts ("expected employer contributions
next year") and context-date typos (American Airlines dated a 2026 share
count in 2027; Edgewell tagged a 2011 quarter as 2012). The loader moves
them to `edgar.facts_quarantine`, and a CHECK constraint on `edgar.facts`
(`period_end <= filed_date`) makes sure none can land there. Nothing is
lost, and no backtest can pick them up by accident.

## 4. Loads

**Bulk (once).** Downloads SEC's nightly `companyfacts.zip` (1.4 GB) and
`submissions.zip` (1.6 GB) and streams them into the tables. No
per-company API calls. Expect 1.5 to 2 hours for the full universe (dev: 13.25M facts in 10
minutes). The
zips are deleted afterwards. The run's `window_end` is the snapshot date.

**Daily.** SEC's monthly XBRL RSS feed lists every XBRL filing. Each run
takes every CIK that filed from 3 days before the last successful
`window_end` through today, then re-pulls its companyfacts and submissions.
A new CIK gets its full history. A known CIK gets the facts filed in the
window plus any filing whose facts never landed, so SEC processing lag
heals itself. Its whole recent filings list (at least a year) is inserted
each time, so non-XBRL forms filed in between are not missed. A missed day
is picked up by the next run.

**Idempotent.** `edgar.facts` and `edgar.filings` are insert-only with
`ON CONFLICT DO NOTHING` on their keys. Rerunning bulk or daily adds zero
rows (verified on dev: 13.25M facts, rerun inserted 0).

**SEC fair access.** Every request sends `SEC_USER_AGENT` (`"Name
email@host"`, env var or Airflow Variable; the loader refuses to start
without it) and the client stays at or under 8 requests per second
(`SEC_MAX_RPS`, hard cap 9). A 403 from SEC stops the run instead of
retrying.

**Scope.** Filings from 2009 on, when tagged numbers start (all filers by
2011). Facts are not date filtered: a 2009 10-K legitimately carries 2007
comparatives. Every taxonomy is kept (`us-gaap` is 97%; `ifrs-full`, `dei`,
`srt` and others follow). Dead and delisted companies stay: Sears, Bed Bath
& Beyond and SVB are all in.

### Setup on a database

```bash
psql "$DATABASE_URL" -f tools/create_edgar_schema.sql   # idempotent
# Airflow: Admin -> Variables -> SEC_USER_AGENT = "Your Name you@example.com"
# Trigger raw_ingest_edgar_bulk; when it succeeds, unpause raw_ingest_edgar_daily.
```

Local / dev runs (bulk can reuse already downloaded files, `--ciks` limits
the load to a sample):

```bash
PYTHONPATH=src python -m datapipeline.ingestion.edgar_to_raw_etl --mode bulk \
    --companyfacts-zip companyfacts.zip --submissions-zip submissions.zip \
    --company-tickers-json company_tickers.json --ciks 320193,789019
PYTHONPATH=src python -m datapipeline.ingestion.edgar_to_raw_etl --mode daily
```

## 5. Open issues

Counts from the 2026-10-20 bulk files (`tools/edgar_open_issues.sql`
recomputes them from the tables).

1. **Tickers that map to more than one CIK: 122 of 29,477.** 121 are a
   delisted symbol (Polygon) that a different company uses today (SEC):
   `AAC` was Ares Acquisition Corp (CIK 1829432) until 2023 and now belongs
   to CIK 2128115. One (`PORT-UN`, a SPAC unit) is inside SEC's own data.
   Ticker to CIK mapping must be dated, not static. (Counted against the
   delisted-only `raw.ticker_metadata` in staging; prod also holds active
   tickers, so rerun the report there.)
2. **CIKs with facts but no ticker: 6,544 of 18,006.** 1,422 still file
   (debt-only issuers, private REITs, subsidiaries, trusts); the rest have
   gone quiet. They cannot be priced, so they drop out of any backtest that
   starts from tickers.
3. **Companies that report in a currency other than USD: 828** (latest
   `Assets` unit), led by CNY 224, CAD 190, EUR 93, BRL 48 and JPY 45. 523
   of them have a current ticker. Most file IFRS 20-F or 40-F (972 use
   `ifrs-full`). Their values need FX conversion before any ratio against a
   USD price.

## 6. For the indicator layer

- Map tags to concepts per period (revenue alone needs at least
  `Revenues`, `SalesRevenueNet`,
  `RevenueFromContractWithCustomerExcludingAssessedTax`,
  `RevenueFromContractWithCustomerIncludingAssessedTax`, and `ifrs-full`
  `Revenue`). Keep the mapping in dbt, not here.
- Fourth quarters are usually not tagged: the 10-K reports the full year.
  Q4 = FY minus the three quarters, each taken as of the same as-of date.
- Shares outstanding: `dei:EntityCommonStockSharesOutstanding` (cover page,
  dated near filing) and `us-gaap:WeightedAverageNumberOfDilutedSharesOutstanding`.
- Split-adjust per-share and share values. Apple's FY2019 diluted EPS is
  11.89 as first reported and 2.97 after the 2020 4:1 split; both rows exist.

## 7. Full statements (`fsn_*`)

`edgar.facts` keeps every total line but drops three things: the splits
inside a line (Apple's Products / Services, segment and region revenue),
company-specific custom tags, and the layout (which statement, line order,
the company's own label). The `fsn_*` tables add them from SEC's
Financial Statement and Notes data sets.

| table | one row per | notes |
|---|---|---|
| `edgar.fsn_submissions` | filing in scope | `accepted_at` is a **reliable** acceptance time (see below) |
| `edgar.fsn_numbers` | number: filing x tag x period x unit x split | compact ids; `dim_id = 0` is the plain total |
| `edgar.fsn_presentation` | line of a statement | `stmt` BS, IS, CF, EQ, CI; `line` order; `plabel` |
| `edgar.fsn_tags`, `edgar.fsn_dimensions` | tag, split | `segments` like `ProductOrService=Product;` |
| `edgar.fsn_files` | data-set zip | load bookkeeping |
| `edgar.fsn_statement_lines` | view | everything joined, readable |

Apple's FY2024 income statement as printed, with splits:

```sql
SELECT line, plabel, segments, value
FROM edgar.fsn_statement_lines
WHERE cik = '0000320193' AND form = '10-K' AND fy = 2024
  AND stmt = 'IS' AND qtrs = 4 AND ddate = '2024-09-30' AND iprx = 0
ORDER BY report, line, segments;
```

**Scope.** Filings by CIKs in `raw.ticker_metadata` or `edgar.company_tickers`.
Every number whose tag is a line on one of the five statements, with all
its splits, including splits shown only in the notes (segment revenue
rides with the revenue line). Numbers that appear only in the notes are
left out. Full history is ~225M numbers, ~40 GB.

**Cadence.** SEC publishes one data set a month (quarterly before
2025-10), so full statements trail the daily totals in `edgar.facts` by up
to a month or so. The weekly DAG loads each new zip once; the first run is
the backfill (79 zips, ~28 GB downloaded one at a time, several hours).

**Point in time.**
- `fsn_submissions.accepted_at` matches SEC's RSS acceptance time for
  7,031 of 7,031 filings checked. About 0.02% of filings have a `filed` date
  before their acceptance day (SEC date adjustments): use the later of the two. It is the right clock for intraday
  rules, and it can also stand in for the unreliable
  `edgar.filings.acceptance_datetime_raw` (join on `accession_number`).
- `fy` / `fp` belong to the filing, as in `edgar.facts`.
- SEC rounds `ddate` to the nearest month end and `qtrs` to whole quarters
  (`datp` / `durp` hold the offsets) and `value` to 4 decimals.
- `iprx = 0` is the primary fact; higher values repeat it at lower precision.
- SEC's `prevrpt` flag (filing amended later) is not loaded: hindsight.
- Same as `edgar.facts`: in 10-Qs the cash flow statement is year to date
  (`qtrs` 2 and 3); Q4 is the year minus nine months.
